## 二、发现的问题（按严重度排序）

### 🔴 P0-1 派工（Dispatch）明细完全信任前端输入，可写入脏数据

**位置**：`PmsProduceOrderController.cs:1248-1373`（Dispatch POST）

**问题**：
1. `t_PMS_BillUseEntry` 的 `BomId/StepId/ItemId/IsProduct/UseNum` 全部取自 `vm.Rows`（前端表单隐藏字段，可被 F12 篡改）。
2. 服务端仅用 `originalByEntry.TryGetValue(r.EntryId)` 匹配做"产成品数量恢复"，但：
   - **`EntryId` 本身是前端提交的临时序号**（`LoadDispatchRows` 里 `entryId++` 从 1 生成，非数据库主键）。
   - 攻击者提交一个**不在 original 里的新 EntryId**，`TryGetValue` 返回 false，`r.UseNum = orig.UseNum` 的产成品保护被**完全绕过**。
   - 更甚者，`rowGroups = vm.Rows.GroupBy(r => r.BomId)` 直接拿前端 BomId 分组，落库的 ItemId/IsProduct/UseNum 也全是前端值 → 可伪造任意领料明细。
3. `productMap = products.ToDictionary(p => p.FBomId, p => p)`（1305 行）：若一个生产单有**两个产出品共享同一 FBomId**（多产品同 BOM），`ToDictionary` 抛 `ArgumentException` → 500。

**风险**：内网 ERP、admin 单用户，实际触发概率低，但属数据完整性硬伤，且多产出同 BOM 是合法业务场景（会直接 500）。

**修复方案**：
```csharp
// 1) 服务端重载真实行，完全忽略前端 Row 的 ItemId/IsProduct/BomId/StepId
var serverRows = LoadDispatchRows(id);   // 真实数据
// 前端只允许提交 (EntryId, UseNum) 两件事
var postedUse = (vm.Rows ?? new List<BillUseDispatchRow>())
    .ToDictionary(r => r.EntryId, r => r.UseNum);

// 2) 用 serverRows 落库，UseNum 只从 postedUse 里按 EntryId 取，产成品强制用服务端值
var rowGroups = serverRows.GroupBy(r => r.BomId).ToList();
// 遍历 serverRows 写 BillUseEntry：IsProduct/ItemId/StepId/BomId 全部来自 serverRows
//   UseNum = r.IsProduct ? r.UseNum : (postedUse.TryGetValue(r.EntryId, out var u) ? u : r.UseNum)
//   （原材料 UseNum 再校验 >= 0）

// 3) productMap 防重复键
var productMap = products
    .GroupBy(p => p.FBomId)
    .ToDictionary(g => g.Key, g => g.First());
```

### 🟠 P1-1 单号并发生成竞态（4 处同源）

**位置**：
- `GoodsApplyController.NextBillNo/NextInterId`（617-629）
- `StockBillController.NextBillNo/NextInterId`（525-541）
- `PmsProduceOrderController.NextBillNo/NextInterId`（1052-1064）
- `PmsProduceOrderController.NextBillUseNo/NextBillUseInterId`（1534-1548）

**问题**：`Max(FBillNo)+1` / `Max(FInterID)+1` 是"读最大值→+1→写入"非原子操作。两个请求并发（两个浏览器同时建单）会拿到**相同的单号/ID**。若 `FInterID`/`FBillNo` 有唯一约束或主键，第二个请求会抛 `DbUpdateException`（主键冲突）导致 500；若无约束，则**产生重复单号**（更糟，静默数据错误）。

**风险**：单机低频操作，概率低但后果严重（重复单号是财务/库存大忌）。

**修复方案**（三选一，按项目现状推荐①）：
1. **事务内串行**：把 `NextBillNo()` 的调用移入 `SaveBill` 的 `BeginTransaction` 事务内，并配合 `Serializable` 隔离级别（或对单号表加 `TABLOCKX`）。
2. **唯一约束兜底**：给 `FBillNo`/`FInterID` 加唯一索引，冲突时重试一次取新号。
3. **专用序列表**：`UPDATE ... SET Seq=Seq+1 OUTPUT inserted.Seq`，天然原子。

> 注：`NextBillNo()` 在 GET（Create/Dispatch）里也调用了一次用于**展示**，实际落库时又调用一次，展示值与落库值可能不一致（并发时更明显）。建议 GET 显示"保存时自动生成"，去掉 GET 里的预取。

### 🟠 P1-2 单号流水溢出未处理

**位置**：
- `GoodsApplyController.cs:621`：`int.Parse(max.Substring(3, 8))` —— 无 try/catch，若流水达到 8 位上限 `99999999`，`no+1` 溢出 `ToString("00000000")` 会输出 9 位 `100000000`（单号变 11 字符，但该处 `Substring(3,8)` 取 8 位固定，Parse 本身在 99999999 时 OK，问题在于**超过 int 范围**或**非数字脏数据**时抛 `FormatException`/`OverflowException` → 500）。
- `StockBillController.cs:533`：同上，`int.Parse(max.Substring(5,8))`。
- `PmsProduceOrderController.cs:1057`：`int.TryParse` 已安全，但 `(no+1).ToString("000000")` 在 no=999999 时输出 7 位 `1000000`（超 6 位定宽）。
- `PmsProduceOrderController.cs:1540`：`NextBillUseNo` 用 `int.TryParse` 安全，但 8 位溢出同上。

**风险**：数据量达到百万级/脏数据时 500 或单号变长。当前数据量下低概率，但属健壮性缺陷。

**修复方案**：
- GoodsApply/StockBill：`int.Parse` 改 `int.TryParse` + 失败回退起始号；或 `long` 兜底。
- 定宽溢出：`(no + 1).ToString("D6")`/`"D8"` 在超位时会原样输出更多位，属可接受（但需确认 DB 列宽）。更稳妥是显式判断 `if (no >= 999999) 报错`。

### 🟡 P2-1 JSON 注入 JS 未做 `</script>` 防护（低风险）

**位置**：
- `PmsBom/Form.cshtml:178-179`：`@Html.Raw(JsonSerializer.Serialize(unitOptions))`、`@Html.Raw(stepDefaultsJson)`
- `PmsItem/Form.cshtml:179`：`@Html.Raw(optTag)`（此条为硬编码中文，安全，忽略）

**问题**：`unitOptions` 来自码表 `DictName`（内部数据，非用户直接输入），若某 DictName 含 `</script>` 或 `</` 序列，会**提前闭合 script 标签**造成 XSS。`JsonSerializer.Serialize` 不会转义 `</script>`。

**风险**：数据来源是内部码表（管理员维护），非外部用户输入，实际风险低。

**修复方案**：序列化后 `Replace("</", "<\\/")` 或 `Replace("<", "\\u003c")`：
```csharp
var safe = JsonSerializer.Serialize(unitOptions).Replace("</", "<\\/");
```

## 五、修复结果（2026-09-07 已完成，逐条 E2E 验证）

### ✅ P0-1 派工明细信任前端 + ToDictionary 重复键（已修 + 已验）

**改动** `PmsProduceOrderController.cs` Dispatch POST：
1. 服务端用 `LoadDispatchRows(id)` 重载真实行，**只信任前端 `(EntryId, UseNum)`**；`ItemId/IsProduct/BomId/StepId` 全部取自服务端真实数据。
2. 未知 EntryId（伪造行）→ `ModelState.AddModelError` 拒绝，不落库。
3. 产成品 `UseNum` 强制取服务端值；原材料 `UseNum < 0` 拒绝。
4. `productMap` 由 `ToDictionary(p=>p.FBomId)` 改 `GroupBy+First`，防多产出同 BOM 的 `ArgumentException`。
5. 连带修复：验证失败重显时 `ProduceOrderId/ProduceOrderNo/ProduceOrderDate/ProductSummary` 由 0/空 恢复为真实值（原 bug：重显表单 action 变 `/Dispatch/0`）。

**E2E 证据**：

### ✅ P1-1 单号并发生成竞态（已修 + 已验）
