## 二、派工（生成领料单）业务规则速记

- 入口：生产单列表「已审核 + 未处理」行 → 查看 / **派工** / 反审核；已领料/已入库仅查看。
- 派工页：`/PmsProduceOrder/Dispatch/{id}`（GET 渲染、POST 保存），文件：
  - `Models/BillUseViewModels.cs`（BillUseDispatchViewModel / BillUseDispatchRow）
  - `Controllers/PmsProduceOrderController.cs`：Dispatch GET/POST、GetWorkShops/GetGroups/GetWorkers 三级联动 AJAX、LoadDispatchRows、BindDispatchExtras、NextBillUseNo/NextBillUseInterId
  - `Views/PmsProduceOrder/Dispatch.cshtml`
- 保存逻辑：按 BOM 分组，每个 BOM 生成一张 `t_PMS_BillUse` 头（FBillType="1"，单号 **LLD+8位流水**）+ `t_PMS_BillUseEntry`（产出品 FIsProduct=1 用 PlanNum，原材料 FIsProduct=0 用 NeedNum，**原材料领用数量可改**）；写 `FPickingStatus=1`/`FBillUseFInterID` 到产品明细；全部产出品派完 → 头表 `FOrderStatus=1`（已领料）+ `FPickNo=LLD单号`（多个逗号分隔，30 截断）。
- BillUseEntry 与生产单的关联：`FProduceNo=生产单号`、`FProduceId=生产单FInterID`（**关联查询用 FProduceId，BillUse 头表没有 FProduceNo 列**）。

## 三、今晚修复的字段写入规则（新世界语义，用户口径）

- **FApplyerID**：表单未选申请人且填了来源要货单号时，服务端兜底取 `t_PMS_GoodsApply.FEmpID`（`ResolveApplyerId`，Create/Edit 均调用）；前端引入要货单时若申请人选项不在当前部门联动范围会动态补 option。
- **FAuditorID / FAuditDate**：用户语义 = **修改人ID / 修改日期**，Edit POST 时与 FModifyerID/FModifyDate 一起更新。
- **FPickNo**：派工后回写领料单号。
- 修单前建立的存量数据已手工回填：SCD000001 → FApplyerID=189、FPickNo='LLD00000001'、其 LLD 明细 FProduceNo/FProduceId 已补。
